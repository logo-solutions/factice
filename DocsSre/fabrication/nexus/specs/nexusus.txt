# Lot 1 – Registry Nexus (pilote service.hra)

Stories du lot 1. Chaque story est autonome : les règles, les chemins, les paramètres et les critères de recette dont elle a besoin sont écrits dans la story elle-même. Aucune lecture d'un autre document n'est nécessaire.

Chaque story a une section **Démo** : la manière de montrer qu'elle est terminée. Les commandes sont à valider sur l'instance avant la recette. Les points marqués **(à confirmer)** dépendent d'une décision ou d'une vérification encore ouvertes.

Variables utilisées dans les démos :
- `NEXUS` : URL de base de l'instance (ex. `http://nexus.local:8081`)
- `APP` : identifiant de l'application, `service.hra`
- `USER_EDITEUR`, `USER_LECTEUR`, `USER_PROMO`, `USER_EXPLOITATION` : comptes de test, mots de passe dans le coffre (jamais dans ce fichier)

- **SBOM** : obligatoire dès le lot 1. Tout artefact promu porte un SBOM CycloneDX.
- **Haute disponibilité** : reportée à un lot ultérieur (offre Pro, base externe, stockage de blobs partagé).

- **Hors périmètre du lot 1** (infrastructure, traitée à part) : sauvegarde et restauration, supervision au-delà de la sonde de santé, rétention et nettoyage du candidat (sauf la politique décrite en S8).

## Epic : Lot 1 – Registry Nexus Pro

### S1 – Dépôts pour le pilote

En tant que responsable plateforme, je veux des dépôts candidat et release pour les formats raw et Docker, afin de cadrer le stockage dès le départ.

Règles :
- Pour chaque format du lot 1 (raw, Docker) : un dépôt **candidat** (hébergé, reçoit les publications de build) et un dépôt **release** (hébergé, reçoit uniquement les artefacts promus).
- Un proxy de dépôt et un groupe de lecture sont décrits en S11, pas ici.
- Chaque dépôt a son propre blob store, nommé comme le dépôt.
- Politique de redéploiement : **candidat** = autorisée (les images candidates sont reconstruites ; voir point 13) ; **release** = refusée (voir S7). Pour le dépôt release, la politique à utiliser est `ALLOW_ONCE` et non `DENY`, sinon la promotion elle-même serait bloquée (voir point 4).
- Validation stricte du type de contenu : activée sur tous les dépôts.
- Accès anonyme : désactivé sur tous les dépôts.
- Aucune politique de nettoyage sur la release.
- Routage Docker : un sous-domaine par dépôt Docker, terminé sur le répartiteur de charge (`docker-candidat.<hôte>`, `docker-release.<hôte>`, `docker-all.<hôte>`). Le domaine réel reste à renseigner à la place de `<hôte>` (voir point 10).
- Création à la main selon un runbook (S9). La même configuration doit pouvoir être reproduite plus tard par un rôle Ansible.

**Démo**
1. Lister les dépôts : `curl -u $USER_LECTEUR "$NEXUS/service/rest/v1/repositories"` → présence de `raw-candidat`, `raw-release`, `docker-candidat`, `docker-release`.
2. Vérifier la politique d'écriture de chaque release : `curl -u $USER_LECTEUR "$NEXUS/service/rest/v1/repositories/raw-release"` → `writePolicy` = `ALLOW_ONCE`.
3. Docker : `docker login docker-candidat.<hôte>` (routage **à confirmer**, voir point 10) → connexion réussie.

### S2 – Chemin et sélecteur de contenu `service.hra`

En tant que responsable de la gouvernance, je veux que tout artefact du pilote soit sous le préfixe `service.hra`, afin qu'une application ne puisse publier que sous son identifiant.

Règles :
- Le premier niveau du chemin est l'identifiant de l'application, en minuscules, stable et unique. Une application ne publie pas sans identifiant enregistré.
- Raw : chemin `<identifiant>/<composant>/<version>/<fichier>`. Candidat : version suivie du numéro de build pour les images dorées ; version éditeur inchangée pour les composants éditeur. Release : version seule.
- Docker : le premier segment du nom d'image est l'identifiant (`service.hra/<image>:<version>`).
- Un sélecteur de contenu limite chaque dépôt hébergé du pilote au préfixe `service.hra/`, pour raw comme pour Docker.
- Une publication sous un autre préfixe est refusée.

**Démo**
1. Publier sous le préfixe : `curl -u $USER_EDITEUR --upload-file test.txt "$NEXUS/repository/raw-candidat/service.hra/app/1.0.0/test.txt"` → `201`.
2. Publier sous un autre préfixe : même commande vers `.../raw-candidat/autre-app/1.0.0/test.txt` → refus (`403`).
3. Vérifier le sélecteur : `curl -u $USER_LECTEUR "$NEXUS/service/rest/v1/security/content-selectors"` → expression du type `path =^ "/service.hra/"`, rattachée aux dépôts du pilote.

### S3 – Rôles et comptes

En tant que responsable de la sécurité, je veux des rôles qui donnent à chacun seulement les droits nécessaires, afin de limiter les accès.

Règles :
- Authentification : comptes locaux tant que l'annuaire d'entreprise n'est pas connecté. Un compte d'administration de secours est documenté (voir point 6).
- Rôles attendus : `lecteur` (lecture des releases) ; `editeur` (publication en candidat, limitée au préfixe de l'application) ; `promotion` (seul rôle autorisé à écrire en release) ; `mutualise-editeur` (publication des images dorées, équipe dédiée) ; `ssi-controle` (lecture transverse, gestion des quarantaines) ; `exploitation` (administration technique, sans publication).
- Un accès anonyme est refusé.
- Les rôles réellement en place (voir « État d'avancement ») diffèrent de cette liste : l'écart est traité au point 6.

**Démo**
1. Anonyme refusé : `curl -I "$NEXUS/repository/raw-release/service.hra/app/1.0.0/test.txt"` → `401` ou `403`, et `curl -s "$NEXUS/service/rest/v1/security/anonymous"` → `"enabled": false`.
2. Lecteur en lecture seule : `curl -u $USER_LECTEUR -X PUT --upload-file test.txt "$NEXUS/repository/raw-candidat/service.hra/app/1.0.0/test.txt"` → refus.
3. Éditeur limité au candidat : même PUT avec `$USER_EDITEUR` vers `raw-release` → refus ; vers `raw-candidat` → `201`.
4. Chaque rôle de la liste existe : `curl -u $USER_EXPLOITATION "$NEXUS/service/rest/v1/security/roles"` → les six rôles présents.

### S4 – Ingestion manuelle dans le candidat

En tant que développeur du pilote, je veux téléverser un artefact et son SBOM dans le candidat selon un runbook, afin de tester le dépôt avant toute automatisation.

Règles :
- Le chemin commence par `service.hra`.
- L'artefact est téléchargeable, avec son empreinte SHA-256.
- Le SBOM est au format CycloneDX JSON, nommé `<composant>-<version>.cdx.json`, rangé à côté de l'artefact. Il contient au minimum les composants et versions, les licences, et la référence du dépôt source et du commit quand ils existent.
- Un téléversement est atomique : artefact, manifeste (S5) et SBOM sont présents ensemble, ou aucun ne reste.

**Démo**
1. Téléverser l'artefact et son SBOM (`app-1.0.0.cdx.json`) sous `service.hra/app/1.0.0/`.
2. Télécharger et comparer l'empreinte : `curl -u $USER_LECTEUR -s "$NEXUS/repository/raw-candidat/service.hra/app/1.0.0/app.tgz" | sha256sum` doit égaler le `sha256` renvoyé par `curl -u $USER_LECTEUR "$NEXUS/service/rest/v1/search?repository=raw-candidat&name=service.hra/app/1.0.0/app.tgz"`.
3. Vérifier la présence du SBOM à côté : même recherche sur `app-1.0.0.cdx.json`.

### S5 – Manifeste de release et attestations signées

En tant qu'auditeur, je veux un manifeste par artefact et des attestations signées qui le lient à l'artefact, afin de vérifier ce qui est promu sans faire confiance à un document saisi à la main.

Règles :
- Le manifeste est déposé à côté de l'artefact, nommé `<composant>-<version>.manifest.json`. Il est la source de vérité des métadonnées que Nexus ne porte pas nativement sur les assets raw.
- Champs du manifeste :

| Champ | Description | Interne | Éditeur (COTS) |
|---|---|---|---|
| `application` | Identifiant d'application | Oui | Oui |
| `composant` | Nom du composant | Oui | Oui |
| `version` | Version publiée | Oui | Oui |
| `build` | Numéro de build | Oui | Non |
| `commit` | Hash complet du commit | Oui | Non |
| `dateCommit` | Date du commit | Oui | Non |
| `dateReception` | Date de réception dans le candidat | Non | Oui |
| `empreinteEditeur` | Empreinte fournie par l'éditeur | Non | Oui |
| `origineSbom` | `genere` ou `reconstitue` | Oui | Oui |
| `imagesDorees` | Versions des images dorées consommées, si connues à la construction | Facultatif | Facultatif |

- Le SBOM et la provenance sont attachés à l'artefact comme attestations, signées (signature keyless, type Cosign ou équivalent).
- La signature est vérifiée avant promotion (intégrée à S6).

**Démo**
1. Ouvrir le manifeste : `curl -u $USER_LECTEUR "$NEXUS/repository/raw-candidat/service.hra/app/1.0.0/app-1.0.0.manifest.json"` → champs `application`, `composant`, `version`, `build`, `commit`, `dateCommit`, `origineSbom` présents.
2. Vérifier la signature (**à confirmer** : Cosign ne signe pas nativement un fichier raw ; méthode probable `cosign verify-blob --bundle`, ou attestation OCI si l'artefact est une image) : `cosign verify-blob --bundle app.tgz.sigstore.json --certificate-identity <identité du workflow> --certificate-oidc-issuer <émetteur> app.tgz` → `Verified OK`.
3. Modifier un octet de l'artefact et relancer la vérification → échec attendu.

### S6 – Promotion candidat vers release

En tant que responsable de la release, je veux promouvoir un artefact du candidat vers la release, afin qu'il soit figé.

Règles :
- La promotion est réservée au compte de promotion. Elle ne se fait jamais par un compte de build.
- Contrôles avant promotion : empreinte de contenu conforme ; manifeste présent et complet ; SBOM présent ; commit présent sur une branche protégée (S10) ; signature vérifiée (S5) ; analyse de licences et de vulnérabilités sans blocage.
- Un échec de contrôle bloque la promotion. L'artefact reste en candidat.
- Docker : la promotion se fait par digest, pas par tag (les tags sont mutables).
- Raw : la méthode officielle dépend de ce que Nexus Pro supporte pour le format raw (**à confirmer**, voir point 3). Repli documenté : republication contrôlée, avec vérification de l'empreinte.
- L'empreinte est identique avant et après la promotion.

**Démo**
1. Docker : noter le digest du candidat (`crane digest docker-candidat.<hôte>/service.hra/app@<digest>`), copier par digest vers `docker-release` (`skopeo copy --all docker://…@<digest> docker://docker-release.<hôte>/service.hra/app@<digest>`), puis vérifier que le digest est identique côté release.
2. Raw, repli par republication contrôlée :
   - `sha256sum app.tgz`, puis `curl -u $USER_LECTEUR -s "$NEXUS/service/rest/v1/search?repository=raw-candidat&name=service.hra/app/1.0.0/app.tgz"` : noter le `sha256` du candidat.
   - Republier le même fichier, avec son manifeste et son SBOM, dans `raw-release` : `curl -u $USER_PROMO --upload-file app.tgz "$NEXUS/repository/raw-release/service.hra/app/1.0.0/app.tgz"`.
   - Vérifier que le `sha256` côté release est identique à celui du candidat.
3. Promotion sans manifeste, puis sans SBOM : tenter avec un candidat incomplet → échec attendu pour chacun.

### S7 – Immutabilité de la release

En tant que responsable de la release, je veux qu'un artefact publié en release ne puisse pas être remplacé, afin de garantir ce qui a été déployé.

Règles :
- Une tentative de republication sur un chemin déjà existant en release est refusée, quel que soit le contenu.

**Démo**
1. Publier une fois : `curl -u $USER_PROMO --upload-file app.tgz "$NEXUS/repository/raw-release/service.hra/app/1.0.0/app.tgz"` → `201`.
2. Republier le même chemin, avec un contenu différent : même commande → refus attendu (code exact à constater sur l'instance).
3. Vérifier que le contenu d'origine n'a pas changé : empreinte identique à celle de S4.

### S8 – Politique de nettoyage du candidat

En tant que responsable plateforme, je veux purger les candidats anciens et non promus, afin de maîtriser le stockage sans jamais toucher à la release.

Règles :
- Critère : candidat non promu et plus ancien que 7 jours (durée à confirmer avec l'exploitation).
- Un candidat promu n'est pas supprimé tant que sa release existe.
- La release n'a aucune politique de nettoyage.
- Les tâches planifiées qui exécutent la purge : « Cleanup repositories using their associated policies » (03 h 00 chaque jour) et « Delete unused manifests and images » (03 h 30 chaque jour) ; la seconde libère l'espace des blobs devenus inutiles.

**Démo**
1. Politique attachée au candidat : `curl -u $USER_EXPLOITATION "$NEXUS/service/rest/v1/repositories/docker/hosted/docker-candidat"` → le champ de politique de nettoyage indique « candidat-7-jours ».
2. Release sans politique : même commande sur `docker-release` → aucun nettoyage.
3. Premier passage : lire le journal des deux tâches après la première nuit, et vérifier qu'aucune image de moins de 7 jours n'a disparu.

### S9 – Runbook d'exploitation

En tant qu'exploitant, je veux un runbook couvrant la création de dépôt, l'ajout d'utilisateur et la promotion, afin de travailler sans connaître Nexus par cœur.

Règles :
- **Critère de recette** : une personne qui n'a jamais utilisé Nexus réalise seule les trois opérations ci-dessous sur l'instance de test, en moins de 60 minutes, sans poser de question à l'auteur du runbook. Toute étape ambiguë relevée est corrigée dans le runbook.

**Démo**
1. Un opérateur (ou un relecteur) suit le runbook à blanc, chronomètre, et note chaque étape ambiguë.
2. Trois opérations à réussir : créer un dépôt de test, ajouter un utilisateur avec le rôle `editeur`, promouvoir un artefact.
3. Le runbook est corrigé à partir des points notés, puis rejoué une fois.

### S10 – Provenance de la promotion

En tant que responsable de la release, je veux qu'une promotion échoue si le commit source n'appartient pas à une branche protégée, afin que seul du code relu soit promu.

Règles :
- Un candidat dont le commit est inconnu, ou hors de la branche protégée `main`, est refusé à la promotion.
- Prérequis côté hébergeur Git (pas dans Nexus) : `main` est une branche protégée, avec pull request obligatoire, statut CI requis, pas de force-push ni de suppression.
- Vérification à intégrer à la promotion : le commit du candidat est un ancêtre de `origin/main`.

**Démo**
1. Pousser un commit sur une branche non protégée, publier un candidat depuis ce commit, tenter la promotion → refus attendu.
2. Publier un candidat depuis un commit de `main` → promotion acceptée.
3. Vérification de provenance : `git merge-base --is-ancestor <sha> origin/main` retourne 0 ; sinon, refus.

### S11 – Proxy et groupe de lecture

En tant que développeur du pilote, je veux tirer les dépendances publiques et les releases par un point d'accès unique, afin de ne consommer que du contenu contrôlé.

Règles :
- Un proxy Docker (`docker-proxy-public`) met en cache les images publiques. Aucun push n'est possible vers un proxy.
- Un groupe de lecture `docker-all` expose la release et le proxy. Le candidat n'appartient à aucun groupe consommé.
- Un déploiement ne tire jamais directement depuis le candidat ni depuis le proxy.

**Démo**
1. Configuration du groupe : `curl -u $USER_LECTEUR "$NEXUS/service/rest/v1/repositories/docker/group/docker-all"` → `memberNames` contient `docker-release` et `docker-proxy-public`, et ne contient pas `docker-candidat` (**à valider**, endpoint à confirmer).
2. Tirage via le groupe : `docker pull docker-all.<hôte>/library/alpine:<tag>` → réussi (routage **à confirmer**, voir point 10).
3. Push refusé sur le proxy : `docker push docker-proxy-public.<hôte>/…` → refus attendu.
4. Tirage du candidat depuis un déploiement : `docker pull docker-candidat.<hôte>/service.hra/app:<tag>` avec le compte de déploiement → refus attendu (ce compte n'a accès qu'à la release).

### S12 – Comptes de service et jetons de build

En tant que responsable de la sécurité, je veux un compte de service par application pour le build, et un compte en lecture seule pour le déploiement, afin qu'aucun script ne porte un compte nominatif.

Règles :
- Un compte de service par application pour la chaîne de build (`svc-build-<identifiant>`), avec jeton d'accès stocké dans le coffre, et rotation périodique.
- Un compte de service en lecture seule pour le pipeline de déploiement, limité aux dépôts release.
- Aucun compte nominatif dans les scripts de build ; aucun secret en clair dans le dépôt.

**Démo**
1. Le build publie avec son jeton, pas avec un compte personnel : `curl -u svc-build-service.hra:$TOKEN --upload-file app.tgz "$NEXUS/repository/raw-candidat/service.hra/app/1.0.1/app.tgz"` → `201`.
2. Le compte de déploiement ne peut pas publier : `curl -u svc-deploy:$TOKEN_DEPLOY -X PUT --upload-file app.tgz "$NEXUS/repository/raw-release/service.hra/app/1.0.1/app.tgz"` → refus.
3. Le compte de déploiement lit la release : `curl -u svc-deploy:$TOKEN_DEPLOY -I "$NEXUS/repository/raw-release/service.hra/app/1.0.0/app.tgz"` → `200`.
4. Rotation : générer un nouveau jeton, mettre à jour le coffre, relancer le build → réussi ; l'ancien jeton → `401`.
5. Contrôle du dépôt : `grep -rn "password\|token" <dépôt de build>` ne trouve aucun secret en clair.

### S13 – Recherche par préfixe

En tant que responsable de la gouvernance, je veux retrouver tous les artefacts d'une application par son identifiant, dans chaque dépôt hébergé, afin de faire un inventaire et un audit.

Règles :
- Une recherche sur `service.hra` renvoie tous les artefacts publiés sous ce préfixe, dans le candidat et dans la release, et aucun autre.
- Le résultat inclut le chemin, l'empreinte SHA-256 et la version.

**Démo**
1. Lister les artefacts du candidat : `curl -u $USER_LECTEUR "$NEXUS/service/rest/v1/assets?repository=raw-candidat"` (suivre le `continuationToken` jusqu'à la fin), puis filtrer les chemins commençant par `service.hra/`.
2. Faire la même chose sur `raw-release`.
3. Comparer au décompte attendu, tenu dans le registre de l'application. Aucun artefact d'une autre application ne doit apparaître.

### S14 – Composant éditeur (COTS)

En tant que responsable de la release, je veux déposer un composant éditeur avec un SBOM reconstitué et marqué comme tel, afin de le promouvoir comme les composants internes sans prétendre qu'il vient de notre chaîne de build.

Règles :
- Le composant éditeur est déposé dans le candidat, jamais proxifié. Son empreinte est comparée à celle publiée par l'éditeur.
- Le SBOM est reconstitué par analyse du contenu. Il porte la propriété `origine = reconstitué par analyse`. Le manifeste porte `origineSbom = reconstitue`.
- Chemin : composant partagé sous `mutualise/<composant>/<version>/` ; composant propre à une application sous `<identifiant>/<composant>/<version>/`. La version est celle de l'éditeur, inchangée.
- Promotion : mêmes contrôles que S6, avec en plus l'empreinte conforme à celle de l'éditeur, le manifeste sans commit, et le SBOM marqué.
- En cas de licence interdite, le composant est mis en quarantaine à l'entrée, et une décision de la sécurité est requise (voir point 7).
- Formats à confirmer : Temurin, MongoDB et MariaDB en raw (voir point 9).

**Démo**
1. Déposer le composant de test et son SBOM reconstitué dans `raw-candidat`, sous `mutualise/temurin/21.0.5/` (exemple ; le composant de test réel reste à choisir).
2. Comparer l'empreinte : `sha256sum composant.tgz` doit égaler la valeur publiée par l'éditeur.
3. Vérifier le marqueur : `jq '.metadata.properties[] | select(.name=="origine")' temurin-21.0.5.cdx.json` → `value` = `reconstitué par analyse`. Vérifier aussi `origineSbom` = `reconstitue` dans le manifeste.
4. Promouvoir par la méthode de S6 : réussi si les contrôles passent ; échec si la licence est interdite ou si le SBOM n'est pas marqué.

## Points ouverts

1. **Édition** : Nexus Pro est retenu, mais l'instance est en Community. À trancher : licence Pro, ou révision de la décision.
2. **Promotion raw** : la méthode officielle n'est pas tranchée. Le repli par republication contrôlée est démontrable dès maintenant (S6, étape 2). Reste à savoir si Nexus Pro offre une promotion native pour le raw.
3. **Immutabilité** : `DENY` bloquerait aussi la première publication, donc la promotion. `ALLOW_ONCE` est le réglage cohérent sur la release, à confirmer sur l'instance Pro.
4. **Formats absents** : Maven, npm et Python sont hors du lot 1. Il faut une date de reprise pour chacun.
5. **Annuaire** : le lot 1 utilise des comptes locaux. Il manque un compte de secours documenté, une date de sortie des comptes locaux, et une décision écrite si l'écart dure.
6. **Rôles** : la liste de S3 (`lecteur`, `editeur`, `promotion`, `mutualise-editeur`, `ssi-controle`, `exploitation`) n'est pas celle des comptes en place (`ci-candidat-push`, `svc-promotion`, `svc-deploiement`, `svc-build-factice-app`). À aligner : soit on crée les rôles de S3, soit on met à jour S3.
7. **Quarantaine** : la recette ne peut pas être complète au lot 1 sans elle. Il faut le noter explicitement comme non couvert, avec la date de reprise.
8. **Sauvegarde** : Nexus est un composant critique de la livraison. Une sauvegarde doit précéder toute donnée réelle.
9. **Formats des composants éditeur** : Temurin, MongoDB et MariaDB en raw, à confirmer.
10. **Routage Docker** : sous-domaine par dépôt, à confirmer ; le domaine interne et le certificat restent à renseigner.
11. **S8 (nettoyage)** : la durée de 7 jours et le périmètre de la purge sont à confirmer avec l'exploitation.
12. **S10 (provenance)** : prérequis côté Git (branche `main` protégée). Sans lui, la vérification de provenance ne protège rien.
13. **Redéploiement du candidat** : la règle attendue est « interdit » pour le candidat aussi. L'instance est configurée en « Allow redeploy » pour `docker-candidat` et `raw-candidat`. Les tags candidats sont uniques par commit, donc « interdit » est possible : à trancher.
